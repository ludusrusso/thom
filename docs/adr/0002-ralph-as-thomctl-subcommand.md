# Ralph as a thomctl subcommand

`thomctl` embeds **Ralph** — the agent loop that drives a PRD to a pull request by repeatedly invoking Claude on its open sub-issues — as a first-class subcommand tree (`thomctl ralph`, `thomctl ralph once`, `thomctl ralph clean`). It is not a sibling shell-script repo, not a Skill, not a Makefile target. We accept that `thomctl`'s scope expands from "tracker-agnostic CLI for PRDs and sub-issues" to "PRDs, sub-issues, and the loop that runs them" — in exchange, the per-project setup collapses to `thomctl init` instead of copy-pasting a `ralph/` directory across every repo, the prompt and Claude settings live in `.thom/ralph/` next to the tracker config (one mental model, one place), the loop's predicate (`open sub-issues == 0`) speaks the same `backend.Backend` interface as the rest of `thomctl` and works on any backend (Jira or GitHub) without a code change, and the no-progress detection (open-set unchanged for 2 iterations) replaces the rc-frontend "trust the loop forever" behaviour that's unsafe under `--afk`. The PR step shells out to `gh` on the assumption that the code host is GitHub regardless of where issues live — a Jira-tracked project hosted on GitHub is the common case, not an edge case, so issue tracker and code host are treated as independent axes rather than collapsed into one `backend` field.

## Considered options

- **Embed in thomctl (chosen).** One CLI, one config dir, the loop's predicate goes through the existing Backend interface, prompt defaults ship in the binary, no per-repo script duplication.
- **External shell scripts copied per-repo (the rc-frontend pattern).** Zero coupling between Ralph and `thomctl`, but every repo has to maintain its own `ralph/` directory; prompt drift across repos; the loop's predicate has to re-implement the parent-issue search per-tracker; `--afk` streaming is a bash-and-jq pipeline that resists testing.
- **A separate `ralph` binary that consumes `thomctl`.** Cleanest separation of concerns, but doubles the install surface (`brew install thomctl ralph`) for one workflow, and the two binaries share so much state (`.thom/config.yaml`, the Backend resolution, the issue listing) that the split is bookkeeping rather than modularity.
- **A Claude Skill that orchestrates `thomctl` from the outside.** Skills can't manage git worktrees or own a long-running loop without delegating to a shell; we'd be back to option 2 wearing a Skill hat.
